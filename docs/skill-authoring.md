# 在本仓库创建 Skill 的最佳实践

这份文档沉淀了创建 `model-thinking-tools` 里 agent skills 的实践经验，供每次新增 / 修改 skill 时参考。它不是教条——**按原理和真实效果取舍，而不是照搬规则**。

来源：Anthropic 的 Thariq Shihipar《Lessons from Building Claude Code: How We Use Skills》、Matt Pocock 的 [skills 仓库](https://github.com/mattpocock/skills)、官方 skill-creator，以及本仓库自己的实跑迭代。

---

## 0. Skill 的结构约定

每个 skill 是一个 kebab-case 目录，内含 `SKILL.md`：

```
<skill-name>/
└── SKILL.md
```

- `SKILL.md` frontmatter 必填 `name`（与目录名一致）和 `description`。
- 复杂内容（>~150 行、或有独立子领域）才拆出 `references/*.md`、`scripts/` 等；本仓库多为纯对话流程，通常单文件即可。
- 新增 skill 后**更新 README 的清单表**。

## 1. 创建一个新 skill 的流程

1. **捕捉意图**：这个 skill 让 Claude 能做什么？何时触发？何时*不*该触发？输出是什么形态？
2. **先 review 计划再动手**：把设计讲清、列出风险/取舍，得到确认后再写正文（不要直接甩成品）。
3. **起草 SKILL.md**。
4. **实跑验证**（交互型 skill 尤其重要）：拿一个真实例子走一遍。**最好用一个你*不是*专家的话题**——才能测出"脚手架能否把非专家带到目标深度"，而不是你自带了能力。
5. **回填 Gotchas**：用实跑*观察到*的真坑，不是预想的坑。
6. **（可选）触发优化**：用 skill-creator 的 `run_loop` 把触发/不触发条件转成评测集，量化触发准确率（单轮、可后台）。

## 2. description：它是触发器，不是摘要

description 是模型决定"要不要加载这个 skill"时**唯一**看到的东西。写法：

- **第一部分**：这个 skill 做什么。
- **第二部分**："当用户……时使用"——列出具体的触发场景、关键词、措辞。
- **第三部分**："不要用于……"——列出**近似负例**（共享关键词但其实该用别的，如"解释一下 X" vs "我想真正搞懂 X"）。
- 略微 **pushy** 一点，对抗模型"漏触发"的倾向（"即使用户没明说……也应触发"）。
- **触发词要覆盖用户实际使用的语言**。本仓库面向中英文用户，所以 description **保持双语**——英文用户得靠英文触发词才能命中。

## 3. 正文：信任模型 + 讲清 why

- **信任模型、别过度铺步骤**。社区标杆（如 Matt Pocock 的 `grill-me`）极简，靠模型能力而非死板 step-by-step。Thariq："给它需要的信息，但留出随机应变的余地。"
- **承重指令只说一次 + 讲清 why**。与其满屏 `MUST`，不如解释*为什么*重要，让模型能在新情境里自己判断。例：与其把"每阶段停下"写六遍，不如说清"用户的选择决定下一阶段内容，预跑=基于猜测、会被推翻、废掉交互"，再在每个决策点放一句极短的提醒。
- **正文语言**：指令用中文（单语，模型中英都懂、翻译指令是冗余）；面向用户的话术给中文范例 + 指示模型"**用用户的语言**作答"；关键术语可并列锚定（如 `模因层（meme layer）`）。

## 4. 多轮 / 行为型 skill 专属

- **加持续性声明**：多轮 skill 会"漂"——跑几轮后模型忘了自己在 skill 里、退回默认行为。明确写"一旦开跑就留在流程里，直到 <退出条件>；不确定时默认仍在流程内"（学自 Matt 的 `caveman`）。
- **"停下等用户"是最难稳的**：讲清 why（见上）+ 在每个该停的点放就地短提醒。

## 5. Gotchas：来自实跑，不靠预想

不要凭空写一堆"预测的失败模式"——那是猜测，且常和正文重复。**先实跑、观察真正崩在哪，再回填。** 每条标注来源（实测 / 潜在风险）。

## 6. 用对比示例（Not / Yes）

一对 `✗ / ✓` 比一段说明更能传达行为规范，尤其对微妙区分（如"换皮的表层理解" vs "真正的深层问题"、"盖章附和" vs "诚实校验"）。学自 Matt 的 `caveman`。

## 7. 压缩与编辑：按行为价值取舍，不按行数

- 行数/字数**不是硬指标**。Matt 主张 <100 行、skill-creator/Thariq 说 <500 行都行——分歧很大，别 cargo-cult。
- 真正的标准：**砍真冗余**（同一指令重复、模型不需要的脚手架）；**留有行为价值的**（承重的 why、可执行的映射、补全边界的兜底、具体示例）——哪怕它让文件变长。
- **压缩后 diff 旧版、逐块复审删除项**，确认没有为了短而误删承重内容，再提交。

## 8. 体裁意识

Thariq 总结的 9 类 skill 全是工程味的（API 参考、CI/CD、runbook…）。本仓库的"思维模型 / 推理引导型"skill 是**另一个体裁**：脚本、config、memory、hooks 多不适用。真正适用的是——description 即触发器、讲清 why、给灵活度、Gotchas，以及（多轮的）持续性声明。
